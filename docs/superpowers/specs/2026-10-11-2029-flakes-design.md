# chreode flakes — design

Status: approved · 2026-10-11

## Why

A flaky test is the gate failing to be **deterministic**: the same change gets
a different verdict on a re-run. Agents learn fast that re-running is cheaper
than fixing, and a suite that "usually passes" stops being selective. The
cheapest test of a fix is also the most dangerous: retries hide flakes, so a
retry that saves the run must leave a trace someone is accountable for.

This layer, extracted from the upstream codebase (planafoot) where it is
mature, makes flakiness **visible, tracked, and escalating**:

1. **Telemetry** — every test that fails and then passes on retry is recorded.
2. **Ledger** — each flaky test gets exactly one open GitHub issue; each
   recurrence adds a comment. At a threshold (default 3) signoff fails until
   the flake is fixed or explicitly snoozed.
3. **Burn-in** — tests added or changed on the branch are run N times with
   retries off before signoff passes, so new flakes are caught before they
   land rather than after three victims.

## Scope

**In:**

- Reporters for Playwright and vitest (≥4), published as subpath exports.
- The flake log (append-only jsonl) and its schema.
- The ledger: GitHub issue file/bump/escalate, run as a built-in signoff phase.
- `chreode flake-report` (manual/CI entrypoint to the same ledger code).
- `chreode burn-in` + a `burnInStep()` config helper.
- A generic flake doctrine doc shipped in the repo (`docs/flakes.md`), linked
  from issue bodies by default.
- sfhousing adoption.

**Out:** quarantine beyond the snooze label (no skip lists — a snoozed flake
still runs and still records); auto-fixing; flake dashboards; planafoot
adoption (planafoot does not consume chreode yet — its scripts are the
reference implementation only); non-GitHub forges.

## The model

```
test run (retries ≥1) ──► reporter ──► .chreode/flakes.jsonl ──► ledger phase ──► gh issues
                          (retry-then-pass)   (append-only)       (always runs     (file / bump /
                                                                   after steps)     escalate → fail)

changed tests (base..head) ──► burn-in step ──► N× each, retries 0 ──► fail on any failure
```

### Flake log

- Path: `<repo root>/.chreode/flakes.jsonl`. Signoff exports the absolute path
  as `CHREODE_FLAKE_LOG` to every step; reporters use it if set, else fall back
  to `<cwd>/.chreode/flakes.jsonl`. Not under `test-results/` — Playwright wipes
  its `outputDir` at start and would delete events an earlier vitest step wrote.
- `.chreode/` must be gitignored (otherwise the post-run dirty-tree check fails
  the run). A new signoff precondition checks this when `flakes` is configured,
  failing with the one-line fix.
- Record (one JSON object per line):

  ```ts
  interface FlakeEvent {
    kind: string;              // issue-title bucket, e.g. 'e2e', 'unit', 'client'
    runner: 'playwright' | 'vitest';
    project: string;           // runner project name ('' if none)
    file: string;              // repo-relative, '/'-separated
    title: string;             // describe chain joined with ' › '
    firstAttemptError: string; // ≤40 lines
    tracePath?: string;        // Playwright trace of the failed attempt
    sha?: string;              // CHREODE_HEAD when run under signoff
    at: string;                // ISO timestamp
  }
  ```

- Malformed lines are skipped on read. Events are deduped by `kind/file/title`
  per report.

### Reporters

- `@mindlace/chreode/reporters/playwright` — default-exported reporter class
  (Playwright loads reporters by specifier). Records on `retry > 0 && passed`
  when an earlier attempt of the same test failed or timed out.
- `@mindlace/chreode/reporters/vitest` — a class to instantiate in the root
  config's `reporters` (vitest reporters are root-level only). Uses
  `onTestRunEnd` + `diagnostic().retryCount`.
- Options (both): `kind?: string | ((project: string) => string)` — default
  `'e2e'` for Playwright, the project name (or `'unit'` if none) for vitest;
  `projects?: string[]` — record only these projects (default: all).
- `file` is made relative to the git root found from the test file, not
  `process.cwd()`, so invoking a runner from a subpackage still yields repo
  paths.
- `playwright` and `vitest` become **optional peerDependencies**; reporters
  import types only, so neither is a runtime dependency of chreode.
- Reporters write regardless of environment; they write nothing when no test
  retried-then-passed. Recording requires retries ≥1 in the runner config —
  the doctrine doc says so, and the ledger can't detect its absence.

### Ledger

Pure logic (`processFlakeEvents(events, ctx, deps)`) with GitHub calls injected,
ported from planafoot's `flake-ledger.ts`; the `gh` adapter reuses chreode's
`Exec` and the integration tests' `gh` shim.

- Issue title: `flake(<kind>): <file> › <title>`, truncated to 256 chars,
  matched exactly against open issues carrying the `flake` label.
- New issue: created with label `flake` (label created on first use if
  missing); body has the first-attempt error, trace path, sha/branch, and a link
  to the playbook (`flakes.playbookUrl`, default: chreode's `docs/flakes.md`).
- Recurrence: comment with an `<!-- chreode:flake-occurrence -->` marker.
  Occurrence count = 1 (the issue) + marker comments.
- Escalation: count ≥ `flakes.threshold` (default 3) and the issue lacks
  `flakes.snoozeLabel` (default `flake-snoozed`) → listed as escalated.
- Listing: `gh issue list --label flake --state open --limit 1000 --json
  number,title,labels` — label filter, not title search, so it doesn't depend
  on search-index lag.

### Ledger phase in signoff

Enabled by a top-level `flakes` config block (presence = on):

```ts
flakes?: {
  threshold?: number;     // default 3
  snoozeLabel?: string;   // default 'flake-snoozed'
  playbookUrl?: string;   // default chreode docs/flakes.md on GitHub
}
```

- Runs **after the steps, whether they passed or failed** — a flake seen in a
  failing run is still a flake, and attributing it to the run that saw it beats
  carrying it to the next run's sha (planafoot's behaviour as a plain step).
  Skipped only if the run never reached the steps (precondition/merge failure).
- Does not hold the machine lock (it's network, not machine load).
- Outcomes:
  - nothing logged → silent;
  - filed/bumped → printed, log cleared;
  - escalation → run fails (if steps passed) with the issue URLs; the status
    description names the escalation;
  - `gh` error → warning, **log kept** for the next run, run not failed (a
    GitHub outage must not block merging; events keep their own `sha`/`at`).
- Partial runs (`--skip`, `--base`) still run the ledger.

`chreode flake-report` runs the same phase standalone (for hosted CI or manual
use): reads the log, reports, exits 1 on escalation.

### Burn-in

`chreode burn-in --base <sha> --head <sha>` selects test files changed in
`base..head` (excluding deletions), newest-first by mtime, and runs each
matching runner's command with retries off. Config:

```ts
burnIn?: {
  repeats?: number;   // default 5
  maxFiles?: number;  // default 12; overflow is listed as skipped, never silent
  runners: {
    name: string;                        // for output
    match: Matcher | Matcher[];          // picomatch, same as rules
    ignore?: Matcher | Matcher[];
    command: (files: string[], repeats: number) => string | string[];
    // string → run once; string[] → run each in sequence (vitest has no
    // --repeat-each, so its command returns N invocations)
  }[];
}
```

- A file matching no runner is not burned in. A file matching several goes to
  the first.
- Commands run from the repo root with inherited stdio; first failure exits 1
  and names the file set and command.
- The `base` is chreode's incremental base (last signoff note or merge-base),
  so a spec is re-burned only when it changes again — matches planafoot.
- `burnInStep({ when, timeoutMs? })` returns a `StepConfig` (`label:
  'burn-in'`, `run: ({base, head}) => 'npx chreode burn-in --base … --head …'`,
  `if: base !== head`, `policeStderr: true`, `timeoutMs` default 10 min).
  `when` is required — chreode can't tell which steps are tests, so the caller
  passes the test steps' triggers. Place it after the test steps in `steps`.
- Burn-in runs with retries 0, so it never writes flake events.
- Recipes in the README: Playwright (`npx playwright test --repeat-each=N
  --retries=0 --project chromium <files>` — pin projects or `--repeat-each`
  multiplies across all of them) and vitest (`N × npx vitest --run --retry=0
  --project <p> <files>`).

## Config validation

`flakes` and `burnIn` join `TOP_KEYS`; unknown nested keys are rejected like
everywhere else. `burnIn.runners` must be non-empty; `threshold`, `repeats`,
`maxFiles` must be positive integers.

## sfhousing adoption

- Add `flakes: {}` and a burn-in step for `test:unit` (vitest projects `server`,
  `client`) and `test:e2e` (Playwright, project `chromium` only).
- Register both reporters; gitignore `.chreode/`.
- **Retries:** sfhousing currently runs 0 retries locally (Playwright
  `retries: CI ? 1 : 0`, vitest none), which makes telemetry inert. Adopt
  planafoot's model: Playwright `retries: 1` locally, vitest `retry: 1` on
  `client` only (server tests stay strict at 0). A retried pass is still a pass
  for the run, but it is now recorded and escalates.

## Testing

- Unit: log read/write/dedupe; ledger file/bump/escalate/snooze/threshold and
  title truncation (port planafoot's specs); burn-in selection (match, ignore,
  cap, ordering, deletions) and command expansion; config validation.
- Reporters: drive each with synthetic runner events (Playwright `onTestEnd`
  sequences; vitest `TestModule`-shaped fixtures) — no real browser.
- Integration: extend `test/integration/signoff.spec.ts` with the `gh` shim
  recording issue calls — a run whose test step writes a flake event files an
  issue; a failing step still reports; three occurrences fail the run; a `gh`
  failure keeps the log.
- One real-runner smoke per reporter (a fixture test that fails on first
  attempt via a marker file) — vitest in the normal suite; Playwright only if a
  browser isn't required (use a non-browser Playwright test).

## Decisions

1. **Ledger is a built-in signoff phase**, not a plain step, for always-run
   semantics and correct sha attribution.
2. **sfhousing turns on local retries** as above (Playwright 1, vitest `client`
   1, `server` 0), so telemetry is live there.
